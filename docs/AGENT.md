# AGENT — PetMatch

**Purpose, inputs, outputs, tools, RAG and web-search policy.**
Sources: course blueprint §6, §7; PetMatch spec §11, §12, §13, §16.

This document describes what the code does today. Where a behaviour is a
deliberate limitation, it says so rather than describing an intention.

---

## 1. What the agent is, and is not

The agent is a **decision-support component**. It gathers evidence, evaluates
criteria and explains a match. A human staff member decides.

Blueprint §6 is explicit that the agent must be a real component and not a
single LLM call: it plans, chooses tools, observes results and revises its
plan. Course requirement 11 asks for it to be built on the **Deep Agent**
infrastructure. PetMatch's reasoning loop is LangChain's
`deepagents.create_deep_agent` (version 0.7.32, on LangGraph), with its
`write_todos` planning tool, bounded by a hard step cap (§4 below). The agent
runs as its own operating-system process.

### The division of labour — the central design decision

Spec §8 states the system "should not depend on an unexplained number
generated by an LLM". So the work is split:

| Deterministic Python | The language model |
|---|---|
| Hard-constraint checks | Interpreting natural-language intent |
| Every criterion score | Choosing which evidence to gather |
| The weighted total | Writing the explanation |
| Ranking order | Phrasing concerns |
| Which fields are missing from a record | Naming what else it would want to know |

**The model never produces a number that reaches the user.** Scores are
reproducible, unit-testable and defensible: asked "why 72?", the system can
show the arithmetic. This also means the whole test suite runs offline.

## 2. Independence

The agent is a separate process, started with the interpreter outside the
project directory (README.md explains why a virtual environment inside
OneDrive corrupts itself):

```bash
<venv>/Scripts/python.exe -m agent_service
```

What it imports, precisely, because this used to be overstated: the agent
imports `app.config`, `app.domain`, `app.infrastructure.models`,
`app.infrastructure.database` and `app.eventstore.store` — the queue *is* a
database table, so it has to be read, and the scorer *is* the domain layer, so
sharing it is the point. It imports **no Flask application, no controller, no
command and no command bus**. There is therefore no code path by which the
agent could approve, reject or alter an application (rule R4), which is the
boundary that actually matters and the one
`tests/agent/test_agent_loop.py::TestAgentLimitations` asserts.

Two consequences of the process split:

- The web application stays responsive while analysis runs.
- The agent can be stopped, restarted or run on another machine without
  touching the web tier.

```
Flask app  ──enqueue──▶  analysis_jobs  ◀──poll──  Agent process
                                                        │ stdio
                                                        ▼
                                                   MCP server
```

## 3. Input

Per blueprint §6.1, each task receives:

| Input | Source |
|---|---|
| The job record | `analysis_jobs` |
| Adopter profile | `get_adopter_profile` MCP tool |
| Animal profile | `get_animal_profile` MCP tool |
| Curated knowledge | ChromaDB via semantic retrieval |
| External information | Tavily web search, only when the gate opens |
| The adopter's own words | The job's `natural_language_query`, for `INTERPRET_INTENT` |

Job types and what the worker does with each:

| Job type | Direction applied | Writes |
|---|---|---|
| `RANK_APPLICANT` | `ANIMAL_TO_ADOPTER` | `match_analyses` + `AIAnalysisCompleted` |
| `FIND_MORE_ADOPTERS` | `ANIMAL_TO_ADOPTER` | `match_analyses` + `AIAnalysisCompleted` |
| `FIND_MY_PET` | `ADOPTER_TO_ANIMAL` | `match_analyses` + `AIAnalysisCompleted` |
| `INTERPRET_INTENT` | — | `analysis_jobs.result_payload` (§10) |

A job of an analysis type without both identifiers is failed with a reason and
counted as skipped, not scored on defaults.

## 4. The loop

`agent_service/loop.py` owns the task; `agent_service/deep_agent.py` owns the
reasoning engine. One task runs in three phases.

### Phase 1 — deterministic prerequisites

Fixed, and deliberately so. They become the loop's first observations.

```
get_adopter_profile   (MCP / stdio)      ─▶ observation 1
get_animal_profile    (MCP / stdio)      ─▶ observation 2
   either not found   ─▶ MissingRecordError, job failed with its reason
calculate_match_score (deterministic)    ─▶ observation 3
note missing record fields               ─▶ missing_information
rag_search            (ChromaDB, local)  ─▶ observation 4
web-search gate       (spec §13)         ─▶ observation 5
```

The agent never scores a record it could not read, and the score exists before
any model is involved. Retrieval runs before the first model turn because
RAG-first is the policy and because a model that answers immediately should
still be answering over evidence.

### Phase 2 — the Deep Agent

```
create_deep_agent(model=LanguageModelChatAdapter, tools=[4 project tools],
                  system_prompt=explanation_system.md,
                  middleware=[TodoListMiddleware, ModelCallLimitMiddleware,
                              ReasoningTraceMiddleware])
agent.invoke(facts + score + criterion breakdown + every observation so far)
  each model turn: the model replies with EITHER a tool call OR its final JSON
    write_todos  ─▶ the plan is kept in the agent state and copied to the trace
    project tool ─▶ MatchAnalysisAgent._dispatch, observation fed back, next turn
    answer       ─▶ the graph ends
  at most AGENT_MAX_REASONING_STEPS model turns
```

The model chooses the tool and its arguments; nothing in the engine chooses
for it (blueprint §6.2). One tool per turn, so every observation is
attributable to the call that produced it.

**The adapter.** `LanguageModelChatAdapter` is a LangChain `BaseChatModel`
that wraps the project's own `LanguageModel` protocol
(`complete_with_tools(messages, tools) -> ModelTurn`). `bind_tools` converts
LangChain tools into the `{"type": "function", ...}` schemas Ollama reads;
`_generate` converts LangChain messages into `ChatMessage` dicts, calls
`next_model_turn`, and converts the `ModelTurn` back into an `AIMessage` with
one tool call, or with the final answer as JSON text. So `OllamaLanguageModel`
is still the real model, and `StubLanguageModel(scripted_turns=...)` drives
the deep agent offline in tests (CLAUDE.md R3). `langchain-ollama` is not
used: it would be a second Ollama client with its own retry and JSON handling,
and it could not be scripted.

**The tools** are the existing `MatchAnalysisAgent` methods, wrapped as
LangChain tools (`as_agent_tool`) with each definition's own JSON schema. The
spec §13 gate, the trace entries and the gap notes therefore behave exactly as
they do in phase 1. The schema is not validated by LangChain, deliberately: the
tools already accept a small model calling `rag_search` with `q` instead of
`query`, and a validation error would waste a turn.

**Middleware in the stack, and why.** deepagents 0.7.32 assembles a default
stack; a harness profile registered for the adapter's provider key
(`petmatch`) slims it for a 3B model on a CPU, where every tool description is
paid for on every turn (§14):

| Middleware | Kept? | Why |
|---|---|---|
| `TodoListMiddleware` (`write_todos`) | **added** | The Deep Agent planning tool; its plan is copied into the trace. Its guidance is the short `prompts/planning_system.md`, not the library's much longer default |
| `ModelCallLimitMiddleware(run_limit=AGENT_MAX_REASONING_STEPS)` | **added** | The step cap, counted exactly in model turns |
| `ReasoningTraceMiddleware` | **added** | Records `write_todos` plans and invented tool names in the session trace |
| `FilesystemMiddleware` | kept, tools hidden | deepagents treats it as protected scaffolding and will not remove it; all eight of its tools (`ls`, `read_file`, `write_file`, `edit_file`, `delete`, `glob`, `grep`, `execute`) are excluded. Nothing here reads files: records come from MCP, guidance from RAG |
| `SubAgentMiddleware` and the `task` tool | **off** | The general-purpose sub-agent is disabled. A sub-agent is a second agent loop at 30–40 s a turn, and one pairing fits one context |
| `SummarizationMiddleware` | **off** | The step cap keeps the conversation far below the context window, and a summary would be an extra model call outside the step budget |
| `PatchToolCallsMiddleware`, `UnsupportedContentMiddleware` | kept | Housekeeping; no model calls, no prompt text |
| Provider prompt caching | kept | No-ops for a non-Anthropic model |

The model therefore sees five tools: the four project tools and `write_todos`.

The run ends for one of four reasons, and each has a defined result and the
same trace entry the hand-written loop it replaced used to write:

| Exit | Trace entry | Result |
|---|---|---|
| The model answered | `final_answer` | Its answer, after the grounding check (§7) |
| `AGENT_MAX_REASONING_STEPS` turns spent (the model-call limit raises) | `step_cap_reached` | Deterministic explanation, plus a `missing_information` line naming the budget |
| `LanguageModelUnavailableError` raised inside the graph | `model_unavailable` | Deterministic explanation, `model_name = deterministic-fallback` |
| `MalformedModelOutputError` after the bounded retries | `malformed_answer` | Deterministic explanation, `model_name = deterministic-fallback` |

LangGraph's `recursion_limit` is derived from the same budget
(`4 × steps + 8` supersteps; one turn and its tool call measure at 3) as a
backstop: the model-call cap always fires first, and LangGraph's recursion
error is treated as the step cap too. Planning spends a turn from the same budget.

An unknown tool name — including a withheld built-in such as `write_file` or
`task` — is *not* an exit: the model is told there is no such tool and asked
again, because small models invent tool names and one bad turn should not
cost the job.

### Phase 3 — grounding and persistence

The answer is checked against the evidence actually retrieved (§7), combined
with the deterministic gaps, and written with its reasoning trace (§8).

## 5. The tool manifest

Four project tools are offered, built per task at runtime
(`build_tool_manifest`), plus the Deep Agent planning tool. No tool can make
or record an adoption decision (§15). Where each description comes from matters, because
the description is the only thing the model reads when deciding:

| Tool | Description written in | Transport | Read-only |
|---|---|---|---|
| `get_adopter_profile` | `mcp_server/server.py` docstring, read at runtime via `ClientSession.list_tools()` | MCP / stdio | yes |
| `get_animal_profile` | `mcp_server/server.py` docstring, read at runtime | MCP / stdio | yes |
| `rag_search` | `LOCAL_TOOL_DEFINITIONS` in `agent_service/loop.py` | in-process | yes |
| `web_search` | `LOCAL_TOOL_DEFINITIONS` in `agent_service/loop.py` | MCP over Streamable HTTP (Tavily) | yes |
| `write_todos` | `PLANNING_TOOL_DESCRIPTION` in `agent_service/deep_agent.py`; contributed by the deep agent's `TodoListMiddleware` | in-process, agent state only | yes — it writes only the plan |

The MCP half is read from the server, not restated here, so docs/MCP.md §5 —
"the docstring is the only thing the model sees" — is literally true. Each
definition carries a name, that description and a JSON parameter schema, and
is wrapped as a LangChain tool for the deep agent, then converted back by the
adapter into the `tools=[{"type": "function", "function": {...}}]` shape
Ollama's chat API expects.

The definitions are cached on the client after the first successful listing:
they cannot change while the server binary does not, and each listing costs a
subprocess start.

**A tool server that cannot be queried is not fatal.** The manifest then holds
the two local tools only, the trace records why, and the shortfall is listed
under `missing_information`. The two records were already fetched in phase 1,
so the analysis still completes.

## 6. Output

### What the model must answer with

Defined in advance per blueprint §6.3, and stated in
`agent_service/prompts/explanation_system.md`:

```json
{
  "reasons": ["..."],
  "concerns": ["..."],
  "missing_information": ["..."],
  "citations": ["space-and-housing.md#apartments"]
}
```

Nothing else is read. A `score` key, a `decision` key or any other invention
is ignored: the loop reads four keys and validates each.

### What is stored

```json
{
  "score": 78,
  "is_disqualified": false,
  "criterion_scores": [
    {"criterion": "daily_availability", "score": 55, "weight": 0.20},
    {"criterion": "experience_level",   "score": 70, "weight": 0.17}
  ],
  "reasons": ["The adopter's apartment suits an animal needing little space."],
  "concerns": ["Two hours a day is at the lower end for a dog of this age."],
  "missing_information": ["Whether anyone is home during the working day."],
  "evidence_sources": [
    {"kind": "rag", "reference": "space-requirements.md#apartments", "cited": true},
    {"kind": "web", "reference": "https://example.org/senior-dog-care", "cited": false}
  ],
  "reasoning_trace": [
    {"step": 1, "action": "get_adopter_profile", "detail": "record returned"},
    {"step": 4, "action": "rag_search", "detail": "query=\"...\" -> 3 relevant passage(s)"}
  ],
  "used_web_search": false,
  "model_name": "qwen2.5:3b-instruct"
}
```

`score`, `is_disqualified` and `criterion_scores` come from the deterministic
scorer; the weights shown are the real `ANIMAL_TO_ADOPTER` values from
`app/domain/matching.py`. `evidence_sources` lists every source the agent
retrieved, with `cited` marking the ones the explanation actually relied on —
so the interface can distinguish "consulted" from "materially affected"
(spec §6.4). `used_web_search` is true only when a search actually returned
something.

Persisted to `match_analyses`. The JSON-shaped columns are `NVARCHAR(MAX)`
because SQL Server 2014 has no JSON type.

## 7. Grounding — the check, not just the instruction

Rule R4 says the agent never invents facts. The prompt says so too, but a
prompt is not an enforcement mechanism: a small model will cite a plausible
filename it never saw. So `agent_service/explanation.py` checks the answer
against the references this task actually retrieved:

1. Every entry in `citations` must name a retrieved passage or a returned
   search URL. Matching is loose in one direction — `space-and-housing.md`
   matches the retrieved `space-and-housing.md#apartments` — so a real
   citation written short still counts, while an invented filename matches
   nothing.
2. Any sentence carrying a bracketed reference that fails the same check is
   dropped, not merely unmarked.
3. Every drop is recorded in the reasoning trace and noted under
   `missing_information`, so a discarded claim is visible rather than silent.
4. If nothing survives, the deterministic explanation is used and
   `model_name` becomes `deterministic-fallback`. Text a model did not write
   is never attributed to it.

A sentence with no bracketed reference is kept: it is grounded in the records
and criterion scores the prompt supplied.

## 8. The reasoning trace

Every step is recorded as `{step, action, detail}` and stored in
`match_analyses.reasoning_trace` as JSON: both record fetches, the score, each
retrieval with its query and result count, each gate decision with its reason,
each tool failure, dropped citations, the manifest offered, the deep agent's
plan (`write_todos`, each step with its status), any invented tool name
(`unknown_tool`), and the final answer or the reason there was none.

`app/templates/matches/analysis.html` renders it under "How the agent
reasoned" when the view model exposes it. It is the audit artefact for
blueprint §6.2: it shows what the agent did, in order, including the turns it
spent on something that did not work.

## 9. RAG

The vector DB holds the project's **curated knowledge base** — never
transactional records (blueprint §11).

```
knowledge/*.md
  → chunk on the documents' own `##` headings, splitting any section longer
    than 1400 characters into windows with 160 characters of overlap
  → embed with nomic-embed-text (768 dimensions, local, no API key)
  → store in ChromaDB, persisted under data/chroma/
  → retrieve top-k semantically, filtered by a distance threshold (420.0,
    squared L2)
  → the agent cites the passages it used
```

**Embeddings are always supplied explicitly.** If they are omitted, ChromaDB
silently downloads its own ONNX model and creates a second, inconsistent
embedding space. Every call in this project passes vectors.

**Retrieval failure is not fatal.** `KnowledgeBase.search` wraps the embedding
and query calls: a stopped Ollama host, a missing embedding model or a corrupt
store logs a warning and returns no evidence. Without that, an embedding
outage failed the whole job, which contradicted the promise that a model
outage costs only the prose.

Corpus (spec §12) — short, curated documents rather than a large corpus:
species care guides, space and activity requirements, child compatibility,
multi-pet households, senior and special-needs animals, and the
organization's own adoption policy.

Retrieval must be **semantic, not keyword** (blueprint §7). The test for this
asks a question sharing no vocabulary with the target chunk and asserts it is
still retrieved (`tests/agent/test_rag_retrieval.py`).

## 10. Web-search policy

Spec §13 requires search to be deliberate rather than automatic. It is
implemented as an explicit gate function, `decide_whether_to_search`, so that
"did the agent correctly decide *not* to search?" is a testable question.

The gate opens only when **all** hold:

1. The question is **not** about the application's own adopter or animal
   records — those come from MCP tools.
2. The agent has not already searched for this task.
3. **RAG retrieval returned nothing above the relevance threshold.**

Rule 3 is the one worth being exact about: **RAG sufficiency wins.** If the
curated knowledge base answered, the gate stays shut — *even for a question
about current or external facts*. A question being external-sounding widens the
gate only when retrieval came back empty; it never overrides an answer the
project curated. That is spec §13's "RAG first, web second" read literally, and
it is what CLAUDE.md R4 says: "Web search runs only when the curated knowledge
base cannot answer."

Both flags are live, which is what makes the policy load-bearing.
`already_searched_this_task` is set the moment the gate opens for the first
time, so one task gets one search. `relevant_knowledge_found` depends on who
is asking:

- **The opening search, which the agent makes itself.** Here it means *the
  curated guides name this animal*. The agent makes two retrievals: one about
  the pairing's situation, and one about the animal ("Saluki dog care needs,
  temperament, exercise and housing"). It then asks
  `knowledge_covers_animal` whether any retrieved passage names the breed as
  whole words, or the species when no breed is recorded. The decision is
  logged as a `knowledge_coverage` step in the trace.
- **A search the model asks for.** Here it means any passage the task already
  holds.

Why the opening search needs the stricter test: a situational question always
matches some generic apartment or exercise guidance. When any retrieved
passage counted as an answer, the gate stayed shut for every pairing. This was
measured on the real corpus. A Greek Tortoise's question read "a calm other…"
and was refused as `REFUSED_RAG_SUFFICIENT` on the strength of the apartment
guide. So was a Border Collie, whose breed the dog guide does cover. With the
stricter test, a breed the 17 guides never mention (Saluki, Weimaraner, Shiba
Inu, Holland Lop and others in the seed roster) opens the gate, while a
covered one (Border Collie, Maine Coon, every exotic species in the roster)
still keeps it shut.

The animal question is the one that goes to the web. It names the animal and
nothing about the adopter, because it leaves this machine.

When the gate refuses, the model is told which rule refused it —
`REFUSED_OWN_RECORDS`, `REFUSED_RAG_SUFFICIENT`, `REFUSED_ALREADY_SEARCHED`,
`REFUSED_EMPTY_QUESTION` — so it re-plans rather than repeating the query.

Further rules:

- Web content never overrides authoritative application data or an explicit
  business rule.
- When external information materially affects an explanation, its URL is
  recorded in `evidence_sources` with `cited: true` and shown in the
  interface.
- `used_web_search` is stored on every analysis, so the proportion of
  analyses that needed the web is auditable.

## 11. Interpreting an adopter's own words

`INTERPRET_INTENT` exists because interpreting free text needs a model, and no
model call may sit in a request path (NFR-3.1). The job carries
`natural_language_query` and optionally `adopter_profile_id`. The worker runs
`IntentInterpreter.interpret` and stores the result as JSON in
`analysis_jobs.result_payload`, with exactly these keys:

```json
{
  "understood": true,
  "species": ["CAT"],
  "size": "SMALL",
  "activity_level": "LOW",
  "temperament": "CALM",
  "good_with_children": true,
  "good_with_other_animals": null,
  "interpretation": "A small, calm cat that is good with children."
}
```

- `species` holds `Species` values; anything the enum does not define is
  dropped rather than defaulted, so an invented species cannot become a filter
  that matches nothing.
- `size`, `activity_level` and `temperament` hold the matching enum value or
  `null`.
- The two boolean fields are `true` or `null`. `false` is never stored:
  nobody asks for an animal that is bad with children, so absence means "no
  constraint".

The prompt (`agent_service/prompts/intent_system.md`) carries several worked
examples rather than one, and two of them are vague descriptions ("a funny
animal", "something cute and friendly") answered with an empty species list
and null criteria. This is measured, not stylistic: with a single filled-in
example, `qwen2.5:3b-instruct` copied it. "happy and friendly" came back as
that example's rabbit/hamster/guinea-pig criteria word for word, and "a
funny animal" became `BIRD`. With the vague examples in place both return no
species, and "fast" maps to `HIGH` activity instead of `LOW`. One known
residue: the 3B model still sometimes reads "nice", "sweet" or "happy" as a
`CALM` temperament, despite a rule saying not to.
- `interpretation` is capped at 200 characters.

`agent_service/intent.py` owns both directions — `intent_to_payload` and
`payload_to_intent` — so the contract cannot drift apart, and the web tier
reads it back through the same validation the model's answer went through.

The job writes **no** `MatchAnalysis` row and **no** domain event: it answers a
question, it does not assess a match. A missing or blank
`natural_language_query` fails the job with that reason and never reaches the
model.

## 12. Caching — NFR-3.3

Before running an analysis the worker looks for a stored `MatchAnalysis` with
the same adopter, animal, direction and application. It reuses that row only
when **both** hold:

1. `generated_at` is later than both `Animal.updated_at` and
   `AdopterProfile.updated_at` — an analysis generated after both records
   last changed still describes the current facts.
2. `model_name` is not `deterministic-fallback`. Such a row is a *degraded*
   result: the score and criterion text, written because no model was
   available. Reusing it would make a temporary outage permanent for that
   pairing, and the seeded data contains 40 of them. A fallback row is
   regenerated as soon as a model is there to write the explanation.

When it is reused the job is completed, the reuse is logged, and it is
counted as `reused` in the worker's statistics.

Otherwise the analysis is recomputed and the existing row is **updated in
place**, keeping its `match_analysis_id` so a link to `/analyses/<id>` stays
valid. Every fresh computation appends `AIAnalysisCompleted`, including a
recomputation.

If either record cannot be read, the analysis is recomputed: inference costs
time, but serving an explanation of facts that may have moved costs
credibility.

## 13. Failure handling

| Failure | Behaviour | Job ends |
|---|---|---|
| Either record not found | `MissingRecordError`, recorded with its reason | PENDING while attempts remain, then FAILED |
| MCP tool raises mid-loop | Observation "tool X failed", a `missing_information` line, loop continues | COMPLETED |
| Tool server cannot be listed | Manifest keeps the local tools, trace records why | COMPLETED |
| No relevant RAG passage | Says so under `missing_information`, and the gate may open for the web | COMPLETED |
| Embedding or Chroma failure | Logged, treated as no evidence | COMPLETED |
| Web search fails or returns nothing | Treated as "no external evidence", never fatal | COMPLETED |
| Ollama unreachable | Deterministic explanation, `model_name = deterministic-fallback` | COMPLETED |
| Unparseable model output | Bounded retry with a stricter instruction, then the deterministic explanation | COMPLETED |
| Model answers but nothing survives grounding | Deterministic explanation | COMPLETED |
| Step cap reached | Deterministic explanation plus a `missing_information` line | COMPLETED |
| Anything else raised in a job | Logged with a traceback, recorded on the job | PENDING while attempts remain, then FAILED |
| Worker killed mid-job | Reclaimed after 15 minutes IN_PROGRESS and re-queued | PENDING, or FAILED when out of attempts |

Note the deliberate asymmetry: a model failure completes the job, because the
deterministic score and the criterion sentences are a real answer. A *data*
failure does not, because there is nothing honest to store.

The deterministic score is always computable, since it depends only on
database records. A total model outage therefore degrades the system to
*scores without prose* — not to no service at all.

## 14. Performance — measured, not assumed

On the project machine (Intel Core Ultra 5 125U, CPU-only inference), with
`qwen2.5:3b-instruct`:

| Path | Prompt | Generated | Measured |
|---|---|---|---|
| JSON mode, one explanation call | ~1,300 tokens | ~140 tokens | 16.2 s originally; 31 s re-measured 2026-09-23 on a loaded machine |
| Tool-enabled turn, model warm | ~1,700 tokens | ~140 tokens | 36–43 s |
| Tool-enabled turn, model cold | ~1,700 tokens | ~140 tokens | 110–145 s, dominated by loading the model |
| Native tool call, short prompt | ~600 tokens | ~40 tokens | 22 s |

Throughput on this hardware is roughly **5–6 generated tokens per second** and
**~80 prompt tokens per second**, so latency tracks prompt size closely.
Enabling tool calling costs a turn about a third more than JSON mode: the
manifest adds ~350 prompt tokens, and JSON mode cannot be used at the same
time because it suppresses tool calls on this stack.

The design consequences, unchanged in direction and sharper in degree:

- **No LLM call may sit in a request/response path** (NFR-3.1). Ranking N
  candidates with N model calls would take minutes at best.
- The deterministic scorer ranks every candidate instantly and synchronously.
- The agent generates explanations only for the results that are asked for,
  asynchronously, through `analysis_jobs`.
- Completed analyses are cached and not recomputed for unchanged inputs
  (§12).
- **The step cap is a latency budget, not only a termination proof.** At
  ~40 s a turn, the default of 8 allows a worst case of several minutes for
  one analysis. Set `AGENT_MAX_REASONING_STEPS=4` for demonstrations; the
  observed behaviour of `qwen2.5:3b-instruct` is to answer on the first or
  second turn when the prerequisites already gathered evidence.

### The Deep Agent engine — measured 2026-10-25

Same machine and model, `AGENT_MAX_REASONING_STEPS=4`, a synthetic
adopter/animal pair through a fake MCP client and the stub search provider
(no database). The machine was loaded, so warm turns varied widely; the old
hand-written loop was timed alternately on the same pairing for comparison.

| Run | Model turns | Wall clock |
|---|---|---|
| Deep agent, cold model | 1 | 113 s, dominated by loading the model |
| Deep agent, warm, curated evidence sufficient | 1 | 27–31 s |
| Deep agent, warm, pairing with gaps (Saluki, hours not stated) | 1 | 36–80 s |
| Old hand-written loop, warm, the same pairing with gaps | 1 | 37–82 s |

The deep agent's own cost is small: building the graph and running its
middleware takes under a second per analysis, and the prompt grows by about
480 characters (the planning guidance) and the manifest by about 615 (the
`write_todos` schema) — roughly 270 tokens, or ~3 s at the measured prompt
rate. Model inference dominates every run. In each of these runs the model
answered on its first turn without planning, which is what the planning
prompt asks for when the evidence in the prompt is enough; even in a
diagnostic run told to plan first, it answered directly. The planning path
itself is proven offline by `tests/agent/test_deep_agent_engine.py`.

Observed model behaviour worth recording: with the prerequisites' evidence in
the prompt, the 3B model usually answers immediately rather than calling a
tool — which is the correct decision and the one the manifest asks for. It
does call tools when the prompt gives it a reason to, and it occasionally
writes a tool call as JSON *content* instead of using the tool-call field;
`agent_service/llm_client.py` recognises that form when the name matches an
offered tool.

## 15. Limitations — binding

From spec §6.4 and blueprint §6.4. These are product requirements.

1. **The agent never makes the final adoption decision.** No code path
   auto-approves. It scores, explains and recommends.
2. **The agent never invents information.** Every claim traces to a retrieved
   passage, a tool result or a search result, and §7 checks it.
3. **Sources are documented** whenever they materially affect a conclusion,
   and marked `cited` when they do.
4. **Authoritative data wins.** Retrieved text cannot override a business
   rule or a database record.
