# AGENT — PetMatch

**Purpose, inputs, outputs, tools, RAG and web-search policy.**
Sources: course blueprint §6, §7; PetMatch spec §11, §12, §13, §16.

---

## 1. What the agent is, and is not

The agent is a **decision-support component**. It assembles evidence,
evaluates criteria and explains a match. A human staff member decides.

Blueprint §6 is explicit that the agent must be a real component and not a
single LLM call: it plans, chooses tools, observes results and revises its
plan. PetMatch's agent does that, and runs as its own operating-system
process.

### The division of labour — the central design decision

Spec §8 states the system "should not depend on an unexplained number
generated by an LLM". So the work is split:

| Deterministic Python | The language model |
|---|---|
| Hard-constraint checks | Interpreting natural-language intent |
| Every criterion score | Writing the explanation |
| The weighted total | Phrasing concerns |
| Ranking order | Naming what information is missing |

**The model never produces a number that reaches the user.** Scores are
reproducible, unit-testable and defensible: asked "why 72?", the system can
show the arithmetic. This also means the whole test suite runs offline.

---

## 2. Independence

The agent is a separate process, started with:

```bash
.venv/Scripts/python.exe -m agent_service
```

It **never imports the Flask application** (rule R2). It receives work by
polling the `analysis_jobs` table and obtains domain records through MCP
tools over stdio. Two consequences:

- The web application stays responsive while analysis runs.
- The agent can be stopped, restarted or run on another machine without
  touching the web tier.

```
Flask app  ──enqueue──▶  analysis_jobs  ◀──poll──  Agent process
                                                        │ stdio
                                                        ▼
                                                   MCP server
```

## 3. Input

Per blueprint §6.1, each task receives:

| Input | Source |
|---|---|
| The job record | `analysis_jobs` |
| Adopter profile | `get_adopter_profile` MCP tool |
| Animal profile | `get_animal_profile` MCP tool |
| Curated knowledge | ChromaDB via semantic retrieval |
| External information | Tavily web search, only when gated in |
| Current search intent | The job's `natural_language_query`, when present |

Job types: `RANK_APPLICANT`, `FIND_MY_PET`, `FIND_MORE_ADOPTERS`,
`INTERPRET_INTENT`.

## 4. The loop

```
claim a PENDING job (status -> IN_PROGRESS)
  │
  ▼
plan: what do I need to answer this task?
  │
  ├─▶ act: choose one tool
  │     · get_adopter_profile   MCP / stdio
  │     · get_animal_profile    MCP / stdio
  │     · rag_search            ChromaDB, local
  │     · web_search            Tavily, only if the gate opens
  │     ▼
  │   observe: fold the result into the working set
  │     ▼
  └── re-plan: do I have enough? if not, loop (max 8 steps)
  │
  ▼
apply deterministic eligibility rules   (spec 10)
  ▼
compute the deterministic weighted score
  ▼
generate an explanation grounded in the gathered evidence
  ▼
persist MatchAnalysis + append AIAnalysisCompleted
  ▼
job -> COMPLETED
```

The step cap (`AGENT_MAX_REASONING_STEPS`, default 8) makes the loop
terminating by construction.

## 5. Output

A single structured JSON object, defined in advance per blueprint §6.3:

```json
{
  "score": 78,
  "is_disqualified": false,
  "criterion_scores": [
    {"criterion": "living_environment", "score": 90, "weight": 0.20},
    {"criterion": "daily_availability",  "score": 55, "weight": 0.18}
  ],
  "reasons": [
    "The adopter's apartment suits an animal needing little space.",
    "Both are low-activity, so daily exercise needs are met."
  ],
  "concerns": [
    "Two hours a day is at the lower end for a dog of this age."
  ],
  "missing_information": [
    "Whether anyone is home during the working day."
  ],
  "evidence_sources": [
    {"kind": "rag", "reference": "space-requirements.md#apartments"},
    {"kind": "web", "reference": "https://example.org/senior-dog-care"}
  ],
  "used_web_search": false,
  "model_name": "qwen2.5:3b-instruct"
}
```

`score`, `is_disqualified` and `criterion_scores` come from the deterministic
scorer. The model contributes `reasons`, `concerns` and
`missing_information`, and may only cite sources present in
`evidence_sources`.

Persisted to `match_analyses`. The JSON-shaped columns are `NVARCHAR(MAX)`
because SQL Server 2014 has no JSON type.

## 6. Tools

| Tool | Transport | Purpose | Read-only |
|---|---|---|---|
| `get_adopter_profile` | MCP / stdio | Structured adopter record | yes |
| `get_animal_profile` | MCP / stdio | Structured animal record | yes |
| `rag_search` | in-process | Semantic retrieval from the knowledge base | yes |
| `web_search` | HTTPS (Tavily) | Current or external information | yes |

The two MCP tools are the course requirement (blueprint §8). Details in
`MCP.md`.

The architectural point: **the agent does not own the application's data.**
It asks for it through tools, exactly as it would for any external service.

## 7. RAG

The Vector DB holds the project's **curated knowledge base** — never
transactional records (blueprint §11).

```
knowledge/*.md
  → chunk by section, roughly 400 tokens with 50 tokens of overlap
  → embed with nomic-embed-text (768 dimensions, local, no API key)
  → store in ChromaDB, persisted under data/chroma/
  → retrieve top-k semantically, with a distance threshold
  → agent cites the chunks it used
```

**Embeddings are always supplied explicitly.** If they are omitted, ChromaDB
silently downloads its own ONNX model and creates a second, inconsistent
embedding space. Every call in this project passes vectors.

Corpus (spec §12) — short, curated documents rather than a large corpus:
species care guides, space and activity requirements, child compatibility,
multi-pet households, senior and special-needs animals, and the
organization's own adoption policy.

Retrieval must be **semantic, not keyword** (blueprint §7). The test for this
asks a question sharing no vocabulary with the target chunk and asserts it is
still retrieved.

## 8. Web-search policy

Spec §13 requires search to be deliberate rather than automatic. Implemented
as an explicit gate function so that "did the agent correctly decide *not* to
search?" is a testable question.

The gate opens only when **all** hold:

1. RAG retrieval returned nothing above the relevance threshold, **or** the
   question concerns current or external facts the knowledge base cannot
   cover.
2. The question is **not** about the application's own adopter or animal
   records — those come from MCP tools.
3. The agent has not already searched for this task.

Further rules:

- Web content never overrides authoritative application data or an explicit
  business rule.
- When external information materially affects an explanation, its URL is
  recorded in `evidence_sources` and shown in the interface.
- `used_web_search` is stored on every analysis, so the proportion of
  analyses that needed the web is auditable.

## 9. Limitations — binding

From spec §6.4 and blueprint §6.4. These are product requirements.

1. **The agent never makes the final adoption decision.** No code path
   auto-approves. It scores, explains and recommends.
2. **The agent never invents information.** Every claim traces to a retrieved
   chunk, a tool result or a search result.
3. **Sources are documented** whenever they materially affect a conclusion.
4. **Authoritative data wins.** Retrieved text cannot override a business
   rule or a database record.

## 10. Failure handling

| Failure | Behaviour |
|---|---|
| Ollama unreachable | Job stays PENDING with `attempt_count` incremented; retried next pass. |
| Model returns unparseable JSON | Bounded retry with a stricter instruction; then FAILED with the raw output recorded. |
| MCP tool error | Logged, recorded under `missing_information`, loop continues with what it has. |
| Web search fails | Treated as "no external evidence"; never fatal. |
| No RAG match | Proceeds on structured data alone and says so in `missing_information`. |
| Step cap reached | Scores on the evidence gathered and notes the cap. |

The deterministic score is always computable, because it depends only on
database records. A total model outage therefore degrades the system to
*scores without prose* — not to no service at all.

## 11. Performance

Measured on the project machine (Intel Core Ultra 5 125U, CPU-only):

| Model | JSON generation | Tool call |
|---|---|---|
| `qwen2.5:3b-instruct` | 16.2 s | 11.3 s |
| `qwen2.5:7b-instruct` | roughly double | roughly double |

**No LLM call may sit in a request/response path** (NFR-3.1). Ranking N
candidates with N model calls would take minutes. Therefore:

- The deterministic scorer ranks every candidate instantly and synchronously.
- The agent generates explanations only for the top results, asynchronously.
- Completed analyses are cached in `match_analyses` and not recomputed for
  unchanged inputs.

The architecture and the hardware agree: the agent is a polling process
precisely because its work cannot block a page load.
